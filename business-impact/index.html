Two complementary KPI families

AI improves old KPIs and creates new ones

Group A is what the business measured before AI arrived. AI should move these numbers. Group B did not exist before: each new failure mode that AI brings needs its own measure. Functional safety works the same way. A new hazard gets a safety measure, and the measure gets a metric that proves it works. So the business case needs both: existing business outcomes to show the value, and new AI governance measures to show the AI behind it can still be trusted.

Group B · KPIs introduced by AI

New risks, new KPIs, and their results

Each risk comes from how agents work, so the answer is in how the workflow is built. Agents run inside a fixed workflow, not on their own. A harness of rules, typed contracts and checks surrounds every model call, and the checks that verify a model are not models themselves. That is what lets the workflow grow without the KPIs drifting.

Result source: Reference run

  • Conditional reasoning escalation

    Are unusual cases routed to the model committee only when needed?

    New risk: Over-escalation: model cost and delay spent on cases that rules can settle.

    Built in: Code, not a model, routes the six-step graph. The committee wakes only when rules and evidence leave a question open.

    6 / 15

    cases reached the committee; 9 were settled by rules and evidence.

  • Model-token consumption

    How much inference is used and at what attributable cost?

    New risk: A new variable cost per invoice that grows with every model call.

    Built in: Rules run first and models last. Tokens are spent only at the steps where the graph calls a model.

    0

    tokens: the reference run calls no provider model.

  • Unsupported-claim detection

    How often is a factual claim rejected by source verification?

    New risk: Hallucination: a fluent claim that no source record supports.

    Built in: A model never grades its own claim. Each claim must match a source record, and Tier 1 rules are plain code.

    1 / 4

    checked claims removed for lack of source support.

  • Human override rate

    How often does a named human change an AI recommendation?

    New risk: Automation bias: people stop challenging the machine.

    Built in: The reviewer gets the evidence and both sides of the debate, not only a verdict, so a challenge stays possible.

    Not measured

    needs real reviewer decisions on AI advice.

  • Guardrail interventions

    How often do sanitization, policy and injection guards intervene?

    New risk: Prompt injection: supplier text that tries to steer the model.

    Built in: Each persona sees only sanitised evidence and at most 8 curated tools. The Attacker probes these guards on copies.

    2 / 6

    committee cases where a guard stepped in: an injected supplier instruction and an over-limit proposal set.

  • Recorded audit events

    Can the workflow reconstruct its decisions and inputs?

    New risk: Opaque reasoning: a decision nobody can rebuild later.

    Built in: Every step writes to one event stream. Past cases never feed a new verdict; they become replay tests, so a verdict can be rebuilt.

    15 / 15

    cases have an event history; trace completeness is not yet scored.

  • Validation processing error rate

    How often do validation runs record execution errors?

    New risk: Agent failures: tool calls, provider outages and malformed output.

    Built in: Typed contracts reject malformed output. A failed agent drops out of the debate instead of guessing.

    1 / 15

    cases with a contained adapter failure; the Opponent contributed nothing.

These design choices follow lessons on running agents at scale from the TUM × BCG lecture series; sources are on Resources.
